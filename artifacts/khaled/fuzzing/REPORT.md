# PDF Upload Fuzzing

SOFTSEC Group Project — Group 13<br>
Khaled Alraas • 16 October 2026

## 1. Purpose and scope

I tested how Tatou's PDF upload endpoint (`POST /api/upload-document`) handles malformed PDFs. The aim was to check that it accepts valid uploads and rejects invalid ones without returning a server error or leaving unexpected files or database records.

I focused on PDF uploads because they involve parsing user-supplied files, saving them to disk, and updating the database. I used valid authentication and a valid filename so the tests would reach the PDF parser. All testing ran locally through Flask's test client, without sending fuzzed requests to the university server.

## 2. Inputs, harness, and environment

I started with a valid, one-page PDF generated by the repository's existing `make_pdf()` test helper using PyMuPDF. It contained the text “Tatou upload validation fixture” and was saved as `corpus/valid.pdf` (855 bytes). During fuzzing, the harness uploaded mutated versions using the filename `fuzz.pdf`.

The harness (`server/fuzzing/fuzz_upload.py`) reuses the repository's existing upload test setup. Each input is tested with a fresh temporary storage directory and SQLite database. A valid test token lets the request pass authentication. An existing document and a file outside the storage directory help detect unintended changes. The temporary test environment is cleaned up after each input.

Atheris is a Python fuzzing tool that automatically mutates inputs and uses code coverage feedback to guide further testing. In this campaign, it repeatedly changes the PDF's bytes to explore different code paths. The harness stops if an unexpected exception or failed assertion occurs. It checks that:

- The API returns 201 (accepted), 400 (invalid input), or 413 (too large).
- Accepted uploads are stored in the correct user directory, with unchanged bytes and the correct reported size.
- Rejected uploads leave no extra files or document records; accepted uploads add only the expected file and document record.
- The existing document and the file outside storage remain unchanged.

The regression test also checks that rejecting the saved failing PDF leaves the version records unchanged.

## 3. Finding: malformed page tree returns HTTP 500

The initial trial completed 100 executions without a detected failure. During the first longer campaign, the harness stopped after 712 executions because a mutated PDF caused the API to return HTTP 500 (“internal server error”). The harness stopped deliberately when its response check failed; this did not mean the application process crashed.

I replayed the saved PDF and obtained the same HTTP 500 response. Investigation traced the failure to `FzErrorFormat: malformed page tree`, raised when PyMuPDF tried to load a page.

The saved input is:

`artifacts/khaled/fuzzing/findings/`<br>

`crash-3d957d1cde31c0fda1bdf167fca856b564083bf1`

**Root cause.** The PDF validator handled some parsing errors but did not catch `FzErrorFormat`, the exception raised by the malformed page tree. This exception reached the application's general error handler, which returned HTTP 500 instead of rejecting the PDF with HTTP 400.

**Fix.** I added `FzErrorFormat` to both exception handlers in `_is_valid_pdf`. The malformed PDF now follows the existing rejection path, which removes the temporary upload and returns HTTP 400 with the message “invalid PDF document”.

**Regression test.** I saved the failing PDF as `test/api/fixtures/malformed-page-tree.pdf` and added a test that uploads it. Before the fix, the test failed because the API returned 500. After the fix, it passed: the API returned 400, no extra files remained, and the existing files and database record counts were unchanged.

## 5. Reproduction and evidence

The commands below set up the environment, run the tests, replay the failing PDF, and start another campaign. Run them from the repository's `server` directory on Linux/WSL with Python 3.12. Package versions are recorded in `artifacts/khaled/fuzzing/baseline/environment.txt`. The new campaign uses a copy of the saved inputs and a separate output directory to preserve the original evidence.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -e ".[dev]"
python -m pip install atheris==3.1.0

# Regression test and all API tests.
python -m pytest test/api/test_file_paths.py::test_upload_rejects_malformed_page_tree -v
SECRET_KEY=local-api-test-key-only python -m pytest test/api -v

# Replay the saved input without generating mutations.
python -m fuzzing.fuzz_upload ../artifacts/khaled/fuzzing/findings/crash-3d957d1cde31c0fda1bdf167fca856b564083bf1

# Repeat the bounded campaign using a separate output directory.
set -o pipefail
run_dir=$(mktemp -d)
cp -r ../artifacts/khaled/fuzzing/corpus "$run_dir/corpus"
mkdir -p "$run_dir/findings"
python -m fuzzing.fuzz_upload "$run_dir/corpus" \
  -max_total_time=600 -max_len=4096 -timeout=10 -seed=1301 \
  -print_final_stats=1 -artifact_prefix="$run_dir/findings/" \
  2>&1 | tee "$run_dir/run.log"
campaign_status=$?
printf 'Exit status: %s\n' "$campaign_status" > "$run_dir/exit-status.txt"
printf 'Saved outputs: %s\n' "$run_dir"
```
The collection of saved inputs (the corpus) grew during testing. Using the same random seed does not guarantee the same results if the inputs, code, or environment change. Replay the saved failing PDF to check the specific bug directly.

The code, PDF inputs, package versions, and exit-status files remain in the repository. The 12 log files are stored separately in the shared Drive folder `artifacts/khaled-specA/fuzzing/`: [open the logs folder](https://drive.google.com/drive/folders/1q-63aPLnRl8yae7VDOEQApZtBQd_GH5v). It also contains `logs-manifest.json`, which records each log's size and SHA-256 checksum. For the final archive, place the log subfolders alongside the repository evidence under `artifacts/khaled/fuzzing/`. The folder structure is:

- `baseline/`: starting code revision, package versions, the original 86-test result, smoke check, and 100-execution trial.
- `campaign-01/`: logs showing discovery, diagnosis, replay, and test results before and after the fix.
- `campaign-02/`: the follow-up campaign log, exit status, and 192-test API result.
- `findings/`: the original PDF that triggered the failure.
- `corpus/`: the starting PDF and inputs generated during fuzzing. Git settings preserve these input files byte-for-byte.

## 6. Limits and work journal

This campaign tested PDF contents using valid authentication and a fixed filename. It did not test other endpoints, authentication failures, large uploads, or simultaneous requests. Testing used Flask's test client and SQLite rather than the deployed server and MariaDB. The harness checked responses and side effects, but could miss a valid PDF being incorrectly rejected. These results do not establish that the application is free of bugs.

The campaign did not include checks for memory errors inside MuPDF's native code.
